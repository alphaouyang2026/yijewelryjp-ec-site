# 语言由 URL 路径前缀决定

日语是默认语言，URL 不带前缀（`/`、`/products/…`）；简体中文和英语加前缀（`/zh/…`、`/en/…`）。语言只由 URL 决定：不按浏览器语言自动跳转，也不把选择存进 cookie。这样分享出去的链接打开后还是分享时的语言，搜索引擎能用 hreflang 分别收录三种语言，CloudFront 也按 URL 自然地分开缓存。页头的语言切换链接到当前页面（含查询参数）在其他语言下的 URL。`<html lang>` 跟着 URL 变，简体中文写作 `zh-Hans`，字体按它切换。

API 返回多语言内容的接口要求 `locale` 查询参数（`ja`、`zh`、`en`），缺少或不支持时返回 400，没有默认值：前端总是知道当前语言，必填让 Hono RPC 的类型强制每个调用都带上，不会因为漏传而在 `/zh/` 页面显示日语。

界面文字不用 i18n 库：每种语言一份 TypeScript 对象，中文和英语资源的类型由日语资源推出，键缺少或多出时类型检查失败；当前语言由 `useLocale()` 从 URL 读出。

## Considered Options

- **子域名（`zh.example.jp`）或 `?lang=` 参数**：子域名要多套证书和 CloudFront 配置；查询参数容易在链接中丢失，搜索引擎也不把它当成不同的页面。
- **按 `Accept-Language` 自动跳转**：分享出去的链接会随对方的浏览器变成别的语言，搜索引擎的爬虫也只能看到一种语言。
- **日语也加 `/ja` 前缀**：更对称，但日语是主要市场，规格要求默认语言不带前缀。
- **react-i18next、FormatJS 等库**：带来插值、复数、按需加载等现在用不到的功能和依赖。三种语言、几十条固定文字，用类型化的对象就能保证键一致。以后需要复数或 ICU 消息格式时再重新评估。
