# 商品目录：每个商品一条 item，列表在应用层计算

单表（`pk`/`sk`）里，商品目录只用两个分区：

- `pk=CATEGORY`，`sk=<类别 slug>`：类别名称（多语言文本）、它在店主排序中的位置和版本号。
- `pk=PRODUCT`，`sk=<商品 slug>`：一个商品的全部内容，包括状态（草稿、上架、归档）、多语言的名称和说明、类别、是否主推、上架时间、店主最后修改的时间、版本号，以及各规格的 SKU、标签、含税价格、在库数和锁定数，和按店主顺序排列的照片（key 和多语言的替代文字，#10；之前写入的 item 没有照片，按没有照片读取）。

全部商品、类别列表、新作、主推都在应用层从"已上架"的商品里筛选、排序得出：每次读出整个 `PRODUCT` 分区。不另外维护"新作"这类索引 item，所以商品更新时没有需要同步的冗余数据。商品详情用 `GetItem` 按 slug 读取。

这样做依赖规格的前提：商品远少于 500 件，流量低。公开目录接口的响应由 CloudFront 缓存约 60 秒，所以读整个分区的次数也很少。#5 中暂定的 `NEW_ARRIVAL` 分区被这个布局取代。

## 写入：版本号和条件写入（#9）

每个商品和类别的 item 都有 `version`：创建时为 1，之后每次写入加 1。后台的修改都带着店主看到的版本号，写入是条件写入（`version = <读到的版本>`）：版本对不上时什么都不写，API 返回 409 `stale_version`，后台提示店主加载最新内容后再操作。这样两个店主（或同一店主的两个标签页）不会互相覆盖。引入版本号之前写入的 item 没有 `version`，按版本 0 读取；写入条件是 `attribute_exists(pk) AND (attribute_not_exists(version) OR version = <读到的版本>)`，所以基于版本 0 的修改可以写入这些 item（之后版本为 1），不需要数据迁移。条件和冲突的判断都在 `catalog/infrastructure/versioned-writes.ts`，商品和类别共用。

- 商品的修改整条 `Put`（内容和规格都在一个 item 里）；规格按 SKU 对应，保留的规格沿用原来的锁定数。店主设置的在库数不能少于锁定数（结账已经锁定的件数必须有货），有锁定数的规格也不能删除；违反时返回 400，什么都不写。所以**以后任何写商品 item 的代码（包括结账锁定库存，#12）都必须同时把 `version` 加 1**，否则店主基于旧版本的保存会覆盖掉新的锁定数。代价是结账锁定库存的同时店主恰好在保存，店主会得到一次 409，重新加载即可。
- 类别改名是对单个 item 的条件 `Update`；排序在一个 `TransactWriteItems` 里给每个类别写入新位置并各自加版本号，任何一个版本对不上就整体不写（一个事务最多 100 个 item，远多于店铺的类别数）。新类别排在最后（现有最大位置加 1）。
- slug 唯一靠 `attribute_not_exists(pk)` 的条件写入保证。SKU 在整个目录内唯一，由应用层在写入前读整个 `PRODUCT` 分区检查；两个店主同时用同一个新 SKU 保存时有极小的竞态窗口，考虑到店主很少，接受这个风险，而不为 SKU 增加索引 item（那会打破"只有两个分区"）。
- 商品和类别都没有删除；不再销售的商品归档。

## Considered Options

- **每个规格一条 item（`pk=PRODUCT#<slug>`）加 GSI 来列出商品**：结账锁定库存时可以只更新规格的 item，但列表要用 GSI 或扫描，CDK 的表和本地建表都要加索引。等结账工单（#12）真的需要时再评估；把规格从商品 item 中拆出来不影响 API 和前端。
- **为新作、主推、各类别分别维护索引 item**：读取更省，但每次上架、下架、改类别都要同步多条 item，容易不一致。对小规模目录不值得。
- **在 DynamoDB 里用 FilterExpression 过滤上架状态**：把"上架"这一领域规则放进基础设施层；数据量小时没有性能上的好处。
