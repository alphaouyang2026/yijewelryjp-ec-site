# 后台订单与发货：快递公司用固定选项，发货通知发送失败时由店主重发

店主在后台查看订单、为已付款的订单标记发货，顾客随即收到发货通知（#14）。订单的存储沿用 ADR 0008：一个 `ORDER` 分区，按订单号排序。

## 订单列表：按订单号倒序读整个分区

订单号以下单时的日本时间开头（ADR 0008），所以按 `sk` 倒序查询 `ORDER` 分区就是新订单在前，不需要索引。不带状态时不显示待付款和已过期的订单：前者还在付款页上，后者从来没有付款，店主都不用处理。带状态时只显示这一种，所以待付款、已过期的订单也查得到。筛选在应用层做，每次读整个分区。

## 快递公司：固定选项加"其他"

快递公司是 `yamato`（ヤマト運輸）、`sagawa`（佐川急便）、`japan_post`（日本郵便）或 `other`。选 `other` 时店主填写公司名称（必填，最多 40 个字符）；其他选项不保存名称，邮件和页面按语言显示公司名（API 的邮件模板和前端的 `carriers` 文字各有一份）。这样名称不会写错，邮件能用顾客的语言写公司名，以后也能按快递公司生成查询链接。运单号必填，最多 40 个字符；输入的首尾空格去掉。

只有已付款的订单可以发货，其他状态返回 409 `invalid_status_transition`；修改带店主看到的版本号，版本不对返回 409 `stale_version`，和后台的商品一样。发货后不能修改快递公司和运单号（规格没有要求，需要时再加）。

## 发货通知：先记发货，再发邮件；失败时由店主重发

发货在一次条件写入里把订单改为已发货，保存发货信息，然后发送发货通知，发出后把 `shipping_notice` 记进订单的 `sentEmails`（和 ADR 0009 的邮件一样）。发送失败时订单照样是已发货，响应和后台的订单里 `shippingNoticeSent: false`，后台提示并提供重新发送的按钮（`POST …/shipping-notice`），它只发还没发出的通知。

Webhook 失败时可以返回 503 让 Stripe 重投；后台的操作没有人重投，所以由店主重发。发信不能和订单的写入放在一个事务里（ADR 0009），"邮件发不出就不让发货"反而要在发信成功后再写订单，写入失败时邮件已经发出、订单却没有发货。先记发货再发邮件，订单状态总是对的，只有通知可能要再发一次。

## 后果

- 订单页的视图和后台的订单共用一个映射（`orderPageView`），发货信息的形状两边相同：`{ carrier, carrierName, trackingNumber, shippedAt }`，`carrierName` 只在 `other` 时有值。
- **列表没有分页：** 每次打开都读整个 `ORDER` 分区。一个订单 item 约 1–2 KB，几千个订单也只是一次几 MB 的查询；订单多到列表变慢时，改为按订单号游标分页（DynamoDB 的 `ExclusiveStartKey`），带状态的筛选可以加稀疏索引。
- 邮件和订单页没有快递公司的查询链接；要加时按 `carrier` 生成（`other` 没有链接）。
- 发货通知的"邮件已发出、记录写入失败"窗口和 ADR 0009 一样存在：店主可能看到"未发出"并重发，顾客收到两封。
