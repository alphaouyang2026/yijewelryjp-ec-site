# 订单与结账：一个事务创建订单并锁定库存，令牌保护付款页的返回

结账（#12）要同时创建订单（订单上下文）和锁定库存（商品目录上下文），两个顾客抢最后一件时只能有一个成功。按 ADR 0002，这由应用层的事务单元完成：共享内核定义 `UnitOfWork`（只有 `commit()`，结果是 `committed` 或 `conflict`），`platform/dynamodb-unit-of-work.ts` 把它实现为一次 `TransactWriteItems`，各上下文的仓储用 `addIn` / `updateIn` 把自己的写入加进去。订单上下文的结账用例启动一个事务单元，调用商品目录应用层的 `reserveStock`（它读商品、按领域规则算出锁定后的商品、把条件写入加进事务单元），再加入新订单的写入，一起提交。两个上下文都只写自己的数据。

## 锁定：商品 item 的版本号作为条件

规格的在库数和锁定数在商品 item 里（ADR 0005），所以锁定是对商品 item 的条件 `Put`：内容是锁定后的商品，版本号加 1，条件是版本号仍是读到的值。DynamoDB 的条件表达式不能做减法（"在库数 − 锁定数 ≥ 数量"写不出来），所以"可售数够不够"在应用层按读到的商品判断，版本号保证判断之后没有人改过它。同一商品的多个规格合并成一次写入（一个事务不能对同一个 item 写两次）。两个结账同时锁定同一件商品时，后提交的事务因条件不符（或 DynamoDB 的 `TransactionConflict`）被取消，返回 `conflict`；结账用例重新读取再试，最多 3 次，这时多半已经可售数不足，返回 409 `unavailable_lines`；3 次都冲突时返回 503 `checkout_busy`。每一轮冲突里至少有一个结账提交成功，所以重试次数不影响"有货就能卖出"。

代价（ADR 0005 已经接受）：结账锁定库存的同时店主恰好在保存这件商品，店主会得到一次 409 `stale_version`，重新加载即可；反过来，店主的保存也会让进行中的结账重试一次。

## 订单的存储

单表里订单用一个分区：`pk=ORDER`，`sk=<订单号>`。订单号是下单时的日本时间（`yyyyMMddHHmmss`）加 `-` 和 4 位随机的 Crockford base32 字母数字（如 `20261028153012-7KQ3`），所以按 `sk` 倒序查询就是新订单在前（后台订单列表 #14 用），订单号本身也短到能在电话里报出来。同一秒内的两个订单靠随机部分区分；万一重复，写入条件 `attribute_not_exists(pk)` 让事务冲突，重试时换一个订单号。小店的订单量远低于单个分区的上限。

订单 item 保存：状态、顾客下单时的语言、每一行的商品 slug、SKU、商品名称和规格标签（多语言文本，按下单时的商品目录）、单价、数量，小计、运费、合计，下单时间，结账令牌，Stripe Checkout Session 的 id（创建付款页之后写入），和版本号（每次修改加 1，条件写入，和商品一样）。行金额由单价和数量算出，不另存。

## 付款页的返回：令牌而不是 Session id

付款页把顾客送回两个前台页面：付款后的感谢页，和不付款返回时的取消页。规格说感谢页"按 Checkout Session id 查询订单"，但 Stripe 只保证在 `success_url` 里替换 `{CHECKOUT_SESSION_ID}`，`cancel_url` 不一定；而按 Session id 查询还要再加一个索引 item。所以两个 URL 都带订单号和结账令牌（`?order=…&token=…`，256 位随机值，创建订单时生成，只有发起结账的浏览器知道），API 按订单号 `GetItem`，再用常量时间比较令牌；令牌不对时和订单不存在一样返回 404。Session id 仍保存在订单上，取消时用它让 Stripe 结束付款页，webhook（#13）则按元数据里的订单号找到订单。

## 取消：先结束付款页，再释放库存

顾客从付款页点"返回"时，前端的 `/checkout/cancelled` 立即取消结账，再转到购物车页。否则锁定要等付款页 30 分钟后过期才释放，顾客回到购物车会看到自己刚要买的最后一件变成"售罄"。取消先请 Stripe 让 Session 过期（之后它再也不能付款），成功后才在一个事务单元里让订单过期、释放库存；如果 Stripe 报告 Session 已经付款，什么都不改，交给付款通知处理；Stripe 请求失败时也什么都不释放（顾客可能还在另一个标签页付款），返回 502，前端照样显示购物车，库存等 Stripe 的过期通知释放。创建付款页失败时同样立即让订单过期、释放库存。

## Consequences

- 付款页 31 分钟后过期：Stripe 要求 `expires_at` 至少在它创建 Session 的 30 分钟之后，按它自己的时钟算，多一分钟避免因为网络延迟或时钟误差被拒绝。
- 订单一旦创建，状态只按规格的生命周期变化；#12 只用到 `pending_payment` → `expired`。付款完成、过期通知由 #13 的 webhook 处理，在那之前订单一直待付款、库存一直锁定。
- 结账接口不要求 CSRF 令牌：别的网站的表单提交是跨站导航，不带 SameSite=Lax 的购物车 cookie，只能结账一个空购物车；取消要求 JSON 请求体，别的网站的表单发不出（同 ADR 0007）。
- 本地开发没有 Stripe 时，开发用的付款替身（`ordering/infrastructure/dev-payments.ts`，只有 `local.ts` 加载）把付款页直接设成感谢页；设置 `STRIPE_SECRET_KEY` 时用 Stripe 的测试模式。
- Stripe 适配器（`ordering/infrastructure/stripe-payments.ts`）没有自动测试，API 测试用内存版 Payments；它在 staging 用测试密钥手动验证。

## Considered Options

- **每个规格一条 item，锁定用 `ADD reservedStock :q` 加条件**：可以只更新规格、不和店主的保存冲突，但 ADR 0005 的列表要靠 GSI 或扫描，条件里仍然算不了"在库数 − 锁定数"（要冗余存可售数）。对小店不值得。
- **先创建 Stripe Session，再锁定库存**：锁定失败时要再让 Session 过期，顾客可能已经打开了付款页；规格的顺序（先锁定、再创建付款页）更简单。
- **按 Session id 建查询用的索引 item**：多一条要一起写的 item，只为满足感谢页的查询方式，而令牌同样只给发起结账的顾客。
- **取消时不释放，等付款页过期**：实现更少，但顾客回到购物车时看到自己锁定的商品不可售，要等 30 分钟。
