# 付款事件按订单状态只处理一次，邮件记录在订单上，失败时让 Stripe 重投

Stripe 用 webhook 通知付款结果（#13）。同一个事件可能投递多次，也可能乱序；付款完成后要在一个事务里把订单标为已付款、把锁定的库存转为已售，再给顾客和店主各发一封邮件。规格要求"每个 Stripe 事件 id 最多处理一次：重复投递不会再次改变状态，也不会再发邮件"。

## 幂等靠订单状态，不另存事件 id

订单状态本身就说明一个事件有没有处理过：完成事件只把待付款的订单改为已付款，过期事件只让待付款的订单过期，每次修改都以订单的版本号为条件（ADR 0008）。所以重复投递的事件看到订单已不是待付款，什么都不改；两个投递同时到达时，后提交的事务因版本号冲突失败，重读后同样什么都不改。不符合订单状态的事件（已付款的订单收到过期事件、已过期的订单收到付款事件）记录日志后忽略，返回 200，Stripe 不再重投。

这样不需要另存"已处理的事件 id"。那张表要和订单写在同一个事务里，还要决定保存多久；而对完成和过期事件，它能挡住的重复投递，订单状态已经挡住了。#15 的退款事件会累加"已退款金额"，没有状态可以判断，到时按退款 id 去重。

## 邮件：订单记录发过哪几封，发送失败返回 503

付款记录和发邮件不能放在一个事务里（SES 不参加 DynamoDB 事务）。顺序是先提交付款，再发邮件，每发出一封就在订单的 `sentEmails` 里记下（下单确认 `order_confirmation`、新订单通知 `new_order_notice`，以订单版本号为条件写入）。某封发送失败时，webhook 返回 503，Stripe 之后重投同一个事件；重投时订单已经付款，只补发 `sentEmails` 里没有的邮件。所以付款只记录一次，每封邮件正常情况下只发一次。只有"邮件已发出、但记录它的写入失败"时，重投会再发一次：邮件是"至少一次"。

## 其他决定

- **验证签名在应用层：** Payments 接口的 `verifyEvent(payload, headers)` 校验签名并把 Stripe 事件转换成领域的付款事件（完成、过期、其他）；签名不对时返回 `invalid`，API 回 400。路由把原始请求体原样交给它，不先解析 JSON，因为签名是对原始字节计算的。
- **顾客资料来自付款页：** 完成事件里的邮箱、电话和收货地址（Stripe 的 `customer_details` 和 `collected_information.shipping_details`）保存在订单上，邮件和订单页都用它。
- **只接受当场付款的方式：** 付款页限制为卡（`allowed_payment_method_types: ['card']`，Apple Pay、Google Pay 属于卡），完成即已付款。便利店付款等方式在完成后才付款，要另外处理 `async_payment_*` 事件，而且付款页 31 分钟就过期，v1 不支持。
- **订单页的令牌就是结账令牌：** 感谢页的地址里已经有它，邮件里的订单页链接也带它；另发一个令牌不会更安全。订单页的语言由 URL 决定，邮件用下单时的语言。
- **感谢页去掉购物车里已买的行，而不是清空购物车：** 规格说订单已付款时清空购物车 cookie。结账时购物车就是订单的各行，所以效果一样；但顾客之后再打开感谢页（例如从浏览器历史），清空会删掉新加入的商品。
- **店主通知的地址暂时是部署设置：** `OWNER_NOTIFICATION_EMAIL`（GitHub 环境变量 → CDK → Lambda），通过店铺设置的 `ownerNotifications()` 读取。#16 的店铺设置可以改为后台编辑，同时加上"店主通知语言"；在那之前通知用日语。
- **发件域名是每个阶段的网站域名：** SES 域名身份由 CDK 创建（Easy DKIM、MAIL FROM 子域名 `mail.<域名>` 的 MX 和 SPF），发件人 `noreply@<域名>`，回复发到店主通知地址。域名根上的 MX、SPF、DMARC 属于域名的邮箱（お名前メール），不由栈管理，避免两边改同一条记录。

## Consequences

- 发给顾客的邮件在 SES 沙盒里会失败（收件人未验证），webhook 一直返回 503，Stripe 在 3 天内重试；生产访问获批（#4）之前，staging 只能用身份域名下的地址或已验证的地址测试顾客邮件。
- 邮件发送失败的 503 会出现在 Stripe 后台的 webhook 日志里；#18 的告警再加上 webhook 失败的监控。
- Stripe 适配器的 `verifyEvent` 和 SES 适配器没有自动测试（API 测试用内存版 Payments 和 Mailer），在 staging 用测试模式手动验证。

## Considered Options

- **每个事件 id 一条 item，与状态变化写在同一事务：** 字面上满足"按事件 id"，但对完成和过期事件是重复的保护，还要给 item 设 TTL。
- **先发邮件再提交付款：** 提交失败时顾客已经收到确认邮件，订单却还是待付款。
- **邮件发送失败也返回 200，只记录日志：** Stripe 不会重投，邮件就丢了，要另做重发机制。
- **另发一个订单页令牌：** 多一个要保存和比较的秘密，而能拿到结账令牌的人和能拿到邮件的人是同一个顾客。
